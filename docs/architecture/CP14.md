## Everyday workflow

1. Click **Alarms** in the Studio header. Enter the existing Node
   server access key, then choose **Connect**.
2. See active and quality-unknown alarms, with severity and a clear
   **Acknowledge** button. Acknowledge marks that the operator saw
   the event: it does **not** clear the physical condition or send a
   write command to any PLC.
3. Open **Event history** to see recent transitions.
4. Engineers can expand **Configure alarm rules** to add up to 64
   \`above\`, \`below\`, or \`equals\` conditions on any Modbus tag.
   Each rule has a tag, label, severity, threshold and configurable
   hysteresis (the API contract supports hysteresis even if the
   compact editor initially uses the default value 0).

The alarm panel refreshes once every four seconds while visible.
No per-symbol polling, new WebSocket, or alarm HTTP fetches when
the panel is closed. Rules are evaluated by the Node server on every
**accepted** source sample, independent of browser subscriptions.

## Correct alarming semantics

- GOOD samples evaluate threshold/hysteresis. State transitions, rather
  than every polling value, create new history entries.
- BAD/STALE/UNCERTAIN samples **do not clear** an active alarm.
  They mark its signal quality unknown until a new GOOD reading.
- Acknowledge requires administrator authorization, is logged, and
  never clears active state. A subsequent activation requires a new
  acknowledgement.
- Monotonic event IDs and a bounded 200-entry in-memory view;
  append-only on-disk JSONL journal with a bounded 4-MiB file plus
  previous rotated file. JSON rule configuration uses atomic replace.
- Startup replay restores unreturned alarm/ACK state but keeps quality
  unknown until live GOOD data arrives.
- If event persistence fails, ACK and alarm clearance fail closed;
  the snapshot exposes a visible storage warning.
- Rule configuration is revision-checked to prevent stale engineering
  browsers from overwriting newer rule changes.
- The existing source reset and multi-device namespace
  \`PLC1/Motor/Run\` carry through without special cases.

## Management and deployment

Routes use the same Bearer token, Origin allowlist and bounded
request parsing as Devices & Tags:
\`GET /api/alarms\`, \`POST /api/alarms/config\`,
\`POST /api/alarms/ack\`.

No \`HMI_ADMIN_TOKEN\` means no exposed alarm management endpoints;
the server can still evaluate previously configured alarms.
The Node listener remains localhost-bound for deployment behind
an authenticated TLS reverse proxy. For site commissioning,
validate thresholds, alarm philosophy, clock synchronization,
operator identities and storage retention policies on real hardware.

CI includes unit tests, live hub/API integration and Playwright UI
tests. It does not replace a plant acceptance test.
