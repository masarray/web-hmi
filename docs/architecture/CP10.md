# CP-10 — Smart Modbus Device & Tag Engineering

Starting point: CP-09 verified main \`7f4fddc5c5edece6f3783a85724db9cc11de7d6c\`.

## FUXA workflow studied

FUXA's \`server/runtime/devices/modbus/index.js\` device/tag mapping and
\`client/src/app/editor/tags-ids-config/\` provide the useful model:
define devices and tags once, bind tags to graphical objects, and let the
server handle acquisition. Web HMI keeps the same workflow while using a
typed shared validator, native Angular signals, and an inline editor instead
of a long modal dialog or imported legacy runtime JavaScript.

## What changed

- **Devices & Tags** in the Angular topbar opens a dedicated mapping table.
- Device hostname/IP, TCP port, Unit ID, poll period and response timeout
  are edited in one place; the last valid configuration is saved locally.
- Add/delete rows, FC01/02/03/04, 0-based addresses, typed values, word
  order, tag searching and increments of 40 visible rows for responsive UI.
- Instant validation and an explicit grouped read request plan (matches
  the Node poller, not a separately maintained browser algorithm).
- Import a validated Modbus configuration JSON file and export the current
  config with no software install. Invalid files cannot overwrite good maps.
- In the selected graphical object's Inspector, choose a mapped tag and
  bind it directly. Previous free-form tag ID editor remains available.
- Server supports explicit **read-only Modbus TCP remote endpoints** through
  \`HMI_SOURCE=modbus-tcp\`; the CP-08/09 \`modbus-lab\` alias continues
  to work. IPv4, IPv6 and hostnames are validated. No implicit network
  scanning, connection attempt on GUI edit, or device writes.
- CP-01–CP-09 native SVG graphical editor, FUXA-attributed assets, status
  quality and existing JSON version 1 remain intact.

## From edited mapping to running server

1. Open **Devices & Tags**, enter PLC address and map the registers.
2. The displayed validation ensures that the table is safe to export.
3. Export **modbus-device.json** and place it in the server's \`config/\`
   folder, e.g. rename as \`config/plant-a.json\`.
4. On the same computer or a server that can reach the PLC network:
   \`HMI_SOURCE=modbus-tcp HMI_MODBUS_CONFIG_FILE=plant-a.json npm run start:server\`.
5. In Preview choose Node.js Tag Server; bind graphical objects to
   configured tag IDs. Server heartbeat and tag quality are independent.

**Important:** The web editor saves/export configuration but does not
silently hot-load it onto the server. Configuration loading happens during
server startup, which prevents a remote browser from redirecting live
device connections without operator control.

## Deployment posture

No fixed loopback restriction exists for **outbound device connections**:
specific industrial IPv4/IPv6 addresses and DNS hostnames may be configured.
The **web server still listens on localhost** by default. For other
operator workstations deploy behind an authenticated TLS reverse proxy or
an internal trusted access architecture; do not expose the current
unauthenticated WebSocket directly to untrusted networks.

All Modbus operations remain FC01/02/03/04 **read-only**. Production
suitability still requires authentication, network segmentation, device
commissioning, workload measurements, alarms and failover appropriate
to the plant. Passing CI is software regression evidence, not proof of
successful operation with every vendor PLC.
